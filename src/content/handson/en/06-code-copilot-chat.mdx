### 6.1 — Save the instruction setup before starting

Before sending the implementation prompt, save the primitives you've created so far so Copilot definitely sees the instruction files and frontend rules in the repository:

```bash
git add .
git commit -m "setup primitives"
git push
```

This gives you a clean checkpoint before Copilot starts planning and editing the project.

<Aside type="positive">

**💡 Terminal tip**: In the VS Code terminal, press **Ctrl+I** to ask Copilot a quick question about the command line or current project. This is **not Agent mode**, and the default model is **Auto**, so don't worry about starting several agent sessions just by asking small terminal questions. Almost nothing is loaded into the context window, so it's far cheaper than any normal session you open in VS Code or the CLI. See [Playbook / Token optimization](https://theomonfort.github.io/theomonfort/en/playbook/token-optimization?present=1&slide=12) for details.

</Aside>

### 6.2 — Switch the model to Claude Opus 4.6 or newer

Click the model selector at the bottom of the Copilot Chat panel and pick **Claude Opus 4.6 or newer** (e.g. Opus 4.6 / 4.8). For complex "scaffold the whole site in one shot" work like this section, a higher-end Opus model keeps quality consistent.

While you're there, also switch **"Default Approvals"** at the bottom of the panel to **"Bypass Approvals"**. Since we're working inside a Codespace sandbox, skipping the per-tool approval prompts is much faster.

### 6.3 — Switch to Plan mode

In Copilot Chat's mode switcher, select **"Plan"**.

<Aside type="positive">

**💡 Tip**: In Plan mode, Copilot focuses on **design and questions** rather than immediately editing files. It will push back on anything ambiguous in the requirements. Keep iterating with it until you're happy with the plan.

</Aside>

### 6.4 — Ask for an implementation plan

Copy the following prompt as-is and paste it into Copilot Chat:

````
Build the Playbook landing page in Japanese only (work on a new branch: `feature/playbook-landing-page`).

Requirements:
* Use `src/content/playbook/ja/*.md` as the source.
* Create `/playbook` with cards grouped by `category` (2 columns of cards).
* Use `src/lib/playbook-categories.ts` for category labels, actor names, avatars, descriptions, colors etc.
* Each card shows icon, title, summary, and uses the `color` frontmatter for colors (`cyan`, `magenta`, `amber`, `green`).
* Add decorative floating assets near the matching SDLC category (about 450px wide):
    * introduction → `public/planet-introduction.webp`
    * plan → `public/planet-plan.webp`
    * develop → `public/planet-develop.webp`
    * review → `public/planet-review.webp`
    * secure → `public/planet-secure.webp`
    * operate → `public/planet-operate.webp`
    * administration → `public/planet-administration.webp`
* Add a subtle small movement to the planet assets.
* Clicking a card opens a detail page that renders the full Markdown.
* Detail page has a “Back to Playbook” button.

Add a top “SDLC navigation chain” above the introduction section:
  Plan → Develop → Review → Test & Secure → Operate
  Each item should be a bordered pixel button using the matching category color, with arrows between items, and should link to the category anchor.

Once `npm run dev` confirms it works, commit and push your changes and open a pull request titled "Playbook site foundations".
````

Copilot may ask you a few questions (package manager, UI framework, deployment target, etc.). It should have read `copilot-instructions.md` and default to Astro / Tailwind / npm, but answer any gaps as they come up.

⏱ About 3 minutes

<Aside type="positive">

**Why it matters**: The Stack rule you wrote in 4.1 and the frontend design tokens from 4.2 pay off here — the plan should come back proposing Astro + Tailwind with the colors you specified.

</Aside>

### 6.5 — Implement with Autopilot

Once you're happy with the plan and your checkpoint is pushed, click **"Start with Autopilot"** to kick off the implementation.

![Start with Autopilot](/theomonfort/handson/img/start-with-autopilot.png)

⏱ About 15 minutes

<Aside type="positive">

**💡 Work in parallel**: While Copilot is implementing, you've got time on your hands — hop over to [Step 7 (REVIEW: Copilot Code Review)](/theomonfort/en/handson/review-copilot-code-review/) and enable **Automatic Copilot Code Review** now. That way, the moment Copilot opens the PR it's working on, the review fires automatically.

</Aside>

Once the implementation is done, start the dev server to check it out:

```bash
npm run dev
```

From the port-forwarding notification, click **"Open in browser"** and try it out.

<Aside type="positive">

**Try this**: Open `/playbook`, check that the category sections use the right colors, the cards are in two columns on desktop, and the planet assets feel large enough. Click a few tiles, confirm the detail pages render the full Markdown, and use the Back to Playbook button. Jot down anything that feels off, UI tweaks you'd like, or features you wish were there (we'll file them as Issues in the next step).

</Aside>

### 6.6 — File the improvements as Issues

Continue from the base site with **8 implementation Issues** that build toward the current Playbook. Each `[playbook:...]` is a stable work key, not a GitHub-assigned Issue number.

| Stage | Work keys | Milestone |
| --- | --- | --- |
| Part 6 / checkpoint1 | Base site already built | Catalogue and Markdown details |
| Cloud Agent (Part 8) | `presentation-core` → `presentation-content` / `mermaid-rendering` / `responsive-navigation` | checkpoint2 |
| Test & Secure (Part 11) | `presentation-tests` | checkpoint3 |
| CLI (Part 13) | `playbook-3d` → `galaxy-audio` | Extend to the existing 3D view |
| Operate (Part 14) | `daily-repo-status` | Daily report |

**`./checkpoint1` prepares these same Issues in Japanese.** If you ran it, reuse them in the Issues tab rather than generating duplicates. The English prompt below uses the same keys. If you jump straight to `checkpoint2` / `checkpoint3`, check which acceptance criteria are already met and work only on the remaining tasks. Repository policies and security settings still need separate setup.

Keep the `[playbook:...]` title keys and `workshop-issue` body markers so the prompt and checkpoint script can recognize existing work. Older repository copies may have a script without Issue seeding; check the Issues tab and use this prompt for missing entries rather than assuming they were created.

<Aside type="negative">
**`presentation-core` is required before testing.** 3D is an extension absent from checkpoints 1–3, not a prerequisite for the presentation tests. Start `galaxy-audio` after merging 3D.
</Aside>
