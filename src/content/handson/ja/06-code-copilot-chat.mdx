### 6.1 — 実装前に instruction setup を保存する

実装プロンプトを送る前に、ここまで作った土台をいったん保存しておきます。これにより、Copilot が instruction file とフロントエンドルールをリポジトリ内の前提として確実に参照できます：

```bash
git add .
git commit -m "setup primitives"
git push
```

これで、Copilot が計画や編集を始める前の安全なチェックポイントを作れます。

<Aside type="positive">

**💡 ターミナルのヒント**: VS Code のターミナルでは **Ctrl+I** を押すと、コマンドラインや現在のプロジェクトについて Copilot に軽く質問できます。これは **Agent モードではありません**。既定のモデルも **Auto** なので、小さな質問をしても複数のエージェントセッションを立ち上げてしまう心配はありません。コンテキストウィンドウにはほとんど何も読み込まれないため、VS Code や CLI で開く通常のセッションよりもずっと安価です。詳しくは [プレイブック / トークン最適化](https://theomonfort.github.io/theomonfort/playbook/token-optimization?present=1&slide=12) を参照。

</Aside>

### 6.2 — モデルを Claude Opus 4.6 以上に切り替える

Copilot Chat 画面下部のモデルセレクターをクリックし、**Claude Opus 4.6 以上**（例：Opus 4.6 / 4.8）を選択します。「サイト全体を一気に組み立てる」ような複雑な作業では、Opus 系の上位モデルを使うと品質が安定します。

あわせて、画面下の **「Default Approvals」** を **「Bypass Approvals」** に切り替えてください。今回はサンドボックスである Codespace で作業しているので、ツール実行のたびに承認ダイアログを挟まずに進めた方が圧倒的に速いです。

### 6.3 — Plan モードに切り替える

Copilot Chat のモード切替えから **「Plan」** を選択してください。

<Aside type="positive">

**💡 ヒント**: Plan モードでは Copilot は **設計と質問** に徹し、すぐにファイルを書き換えません。要件が曖昧な部分は逆質問してきます。納得できる計画になるまで対話を重ねましょう。

</Aside>

### 6.4 — 実装計画を依頼する

以下のプロンプトをそのままコピーして Copilot Chat に貼り付けてください：

````
日本語のみの Playbook 一覧ページを作成してください（新しいブランチ `feature/playbook-landing-page` で作業してください）。

要件:
* `src/content/playbook/ja/*.md` をソースとして使う。
* `/playbook` を作成し、カードを `category` ごとにグループ化する（カードは 2 カラム）。
* カテゴリのラベル、担当者名、アバター、説明、色などは `src/lib/playbook-categories.ts` を使う。
* 各カードには `icon`、`title`、`summary` を表示し、色には frontmatter の `color` を使う（`cyan`、`magenta`、`amber`、`green`）。
* 対応する SDLC カテゴリの近くに装飾用の惑星画像を配置する（幅は約 450px）:
    * introduction → `public/planet-introduction.webp`
    * plan → `public/planet-plan.webp`
    * develop → `public/planet-develop.webp`
    * review → `public/planet-review.webp`
    * secure → `public/planet-secure.webp`
    * operate → `public/planet-operate.webp`
    * administration → `public/planet-administration.webp`
* 惑星画像には、控えめな小さい動きを付ける。
* カードをクリックすると、Markdown 全文をレンダリングする詳細ページを開く。
* 詳細ページには「Playbook に戻る」ボタンを置く。

introduction セクションの上に「SDLC ナビゲーション」を追加する:
  Plan → Develop → Review → Test & Secure → Operate
  各項目は、対応するカテゴリカラーを使った枠線付きのピクセル風ボタンにする。項目間には矢印を置き、各ボタンはカテゴリのアンカーにリンクする。

`npm run dev` で動作確認できたら、変更をコミット / プッシュし、"Playbook site foundations" というタイトルでプルリクエストを作成する。
````

Copilot がいくつか質問してくる場合があります（例：パッケージマネージャー、UI フレームワーク、デプロイ先など）。`copilot-instructions.md` を読んでいるはずなので Astro / Tailwind / npm を前提に答えてくれるはずですが、不足があれば回答してあげましょう。

⏱ 約3分

<Aside type="positive">

**ポイント**: 4.1 で書いた技術スタックのルールと、4.2 のフロントエンド用デザイントークンがここで効きます。Plan モードの提案は Astro + Tailwind + 指定カラーになるはずです。

</Aside>

Plan に納得したら **「Start with Autopilot」** をクリックして実装を開始します。

⏱ 約15分

<Aside type="positive">

```bash

```

<Aside type="positive">

**やってみよう**: `/playbook` を開き、カテゴリごとの色、デスクトップでカードが 2 カラムになっていること、惑星画像が十分大きく見えることを確認します。いくつかタイルをクリックし、詳細ページで Markdown 全文が表示されること、「Playbook に戻る」ボタンで戻れることも確認しましょう。挙動がおかしい箇所、UI の改善点、追加したい機能などをメモしておきましょう（次のステップでまとめて Issue 化します）。

</Aside>

### 6.6 — 改善点を Issue 化する

ここからは、基本サイトを現在の Playbook に近づける **8 件の実装 Issue** で進めます。`[playbook:...]` は固定の作業キーであり、GitHub が付ける Issue 番号ではありません。

| 段階 | 作業キー | 到達点 |
| --- | --- | --- |
| Part 6 / checkpoint1 | 基本サイトは実装済み | 一覧と Markdown 詳細 |
| Cloud Agent (Part 8) | `presentation-core` → `presentation-content` / `mermaid-rendering` / `responsive-navigation` | checkpoint2 |
| Test & Secure (Part 11) | `presentation-tests` | checkpoint3 |
| CLI (Part 13) | `playbook-3d` → `galaxy-audio` | 現在の 3D ビューに拡張 |
| Operate (Part 14) | `daily-repo-status` | 日次レポート |

**`./checkpoint1` は以下と同じ日本語 Issue を準備します。** 実行済みなら Issues タブで再利用し、重複作成しないでください。`checkpoint2` / `checkpoint3` から直接始めた場合は、既に満たす完了条件を確認し、未完了の作業だけ進めます。リポジトリのポリシーやセキュリティ設定は別途必要です。

プロンプトとスクリプトが既存作業を識別できるよう、タイトルの `[playbook:...]` キーと本文の `workshop-issue` マーカーを残してください。古いリポジトリのコピーでは Issue を準備しない旧スクリプトの場合があります。作成済みと決めつけず、Issues タブを確認し、不足分だけこのプロンプトで準備してください。

`checkpoint1` は stash やブランチ切り替えの前に Issue を準備し、既存の open / closed Issue は変更せず再利用します。スナップショットが `main` と同じ場合も、新しい PR を作らず不足する Issue を準備します。Issue の準備に失敗したら、表示されたエラーを解消して `./checkpoint1` を再実行してください。作成済みの Issue は保持されます。別 clone を含め、同じリポジトリで同時に複数の取り込みを実行しないでください。`checkpoint2` / `checkpoint3` は Issue を準備しません。

<Aside type="negative">
**`presentation-core` はテストの前に必須です。** 3D は checkpoint1〜3 には含まれない追加実装で、プレゼンのテストを始める条件ではありません。`galaxy-audio` は 3D のマージ後に進めます。
</Aside>

通常の Part 6 では、次のプロンプトを Copilot Chat に送って Issue を準備します。これは実装の依頼ではありません。

```
github-issues skill を使い、自分のこのリポジトリに以下の Issue を準備してください。実装はまだ開始しないでください。
open / closed の両方を確認し、本文の workshop-issue マーカーまたはタイトルの [playbook:キー] が一致すれば既存 Issue を再利用してください。既存の本文を書き換えたり、closed を自動で再オープンしたりしないでください。
存在しない Issue だけを、以下のタイトルと本文（マーカーを含む）で作成してください。ラベルや Organization の Issue Type がなくても作成できるよう、それらを必須にしないでください。
既に実装済みの作業は完了条件を確認して報告し、GitHub の Issue 番号ではなく作業キーで依存関係を判断してください。
```
