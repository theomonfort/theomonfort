### 9.1 — Presentation モードのテストを作成する

#### 公式エージェントを安全に準備する

**更新済み Codespace では Playwright と Chromium を利用できます。** それ以外では Node 22 を使い、以下の依存関係とブラウザーを準備します。Codespaces でプロジェクト依存関係だけが不足する場合は、最初のコマンドだけ実行してください。テスト MCP は次の手順で設定します。

```bash
npm install --save-dev --save-exact @playwright/test@1.58.2
npx playwright install chromium
```

プロジェクトのルートで **公式エージェントを生成**します（VS Code 1.105 以降）。

```bash
npx playwright init-agents --loop=vscode
```

次のファイルは **自動生成**されます。手書きする必要はありません。

```text
.github/agents/
  playwright-test-planner.agent.md
  playwright-test-generator.agent.md
  playwright-test-healer.agent.md
```

初期化時には `.vscode/mcp.json` とサンプルの seed / setup ファイルも生成されます。既存のファイルと workflow は残してください。[Part 3](/theomonfort/handson/plan-mcp/) のルート設定では、生成した `playwright-test` エントリを `.mcp.json` に統合してエージェントを接続するよう Copilot に依頼します。Context7 と他の既存ワークスペースサーバーは残してください。GitHub は組み込みを使い、重複エントリを追加しないでください。ルートファイルの置換やサーバーの二重起動は避けてください。

`playwright.config.ts` がなければ、`testDir: './tests/e2e'` で設定するよう Copilot に依頼します。

**Customizations → MCP Servers → Workspace** で **`playwright-test`** を起動し、信頼確認を行います。コマンドは `npx playwright run-test-mcp-server --headless` で、このプロジェクトから Node 22 で実行します。**Customizations → Agents** で生成したエージェントを確認してください。

#### 実装前にテストを相談する

**`.github/copilot-instructions.md`** に、既存の指示を残して次のルールを追加します。

```text
機能の追加や変更時には、テストが必要かを検討する。適切なテストを提案し、どれを追加または更新するかユーザーに確認してから、機能と合意したテストを一緒に実装する。
ブラウザーの E2E テストでは、`playwright-test-planner` でテスト計画を提案し、ユーザーの承認後に `playwright-test-generator` でテストを作成または更新する。
```

#### 画面を調べ、提案から選ぶ

Chat のエージェント選択で **`playwright-test-planner`** を選び、起動中のサイトの URL を入れて送信します。

```text
テスト MCP で <起動中のサイトのURL> の Playbook プレゼン画面を調べてください。
矢印キー、Escape、スライドリンクの再読み込みなど、不足する有用なテストを
期待結果とともに specs/presentation.md に提案してください。
どれを追加するか私に質問して待ってください。まだ生成しないでください。
```

ブラウザーツールが実際に動いたことを確認し、**`specs/presentation.md`** の全テストケースをレビューします。

#### 選んだテストを生成して実行する

**`playwright-test-generator`** を選び、**`specs/presentation.md`** を添付して送信します。

```text
添付した specs/presentation.md の全テストケースを承認します。
ケースの選択を再確認せず、すべて tests/e2e/presentation.spec.ts に生成してください。
実際のブラウザーでセレクターと意味のある assertion を確認し、重複や固定待機は避けてください。
完了したら自分で起動したブラウザーと preview を閉じ、本当のアプリの不具合は隠さず報告してください。
```

通常の **Agent** に戻り、**「テスト MCP の preview を止め、計画内の全テストと通常のテスト一式を実行してください。assertion を1つ選び、検知する回帰を説明してください」** と依頼します。停止するのは演習で起動したものだけです。任意の **healer** も、テストの skip、削除、assertion の弱体化で成功させてはいけません。

### 9.2 — Web とデスクトップでツールを選ぶ

- **localhost を含む Web：** Playwright とテストエージェント。
- **ネイティブのデスクトップ UI：** 対応と権限がある環境の Computer Use、または専用ツール。万能なテストフレームワークではありません。
- **ロジックや API：** ユニットテストや API テストの方がシンプルな場合があります。

### 9.3 — 合意したテストを PR の CI で実行する

演習の **`test-creation`** ブランチのまま、**`playwright-test-generator`** から通常の **Agent** に切り替えて依頼します。

```text
pull request ごとに tests/e2e のテストを実行する GitHub Actions ワークフローを作成してください。
Node 22、npm ci、対応する Chromium を使い、headless で実行してください。
失敗時のテストレポートをアーティファクトとして保存してください。
```

### 9.4 — PR を確認してからセキュリティへ進む

コミットして push し、既存 Issue に関連付けたテスト PR を作ります。Actions のチェックとレポートを確認してください。前提の PR（利用した場合は checkpoint2 も）を先にレビューしてマージし、続けてテスト PR をマージします。合意したテストと指示を残し、この段階ではチェックポイントを取り込みません。
